# 改写决策契约

本文件供 `shuorenhua/SKILL.md` 按需读取。它只描述文本改写的专业判断；项目级授权、工具权限和停止条件以根 `AGENTS.md` 为准。

## 1. 场景判断

先选一个主场景，混合文本以一个主语域为主，其余语域只保留必要信息。

| 场景 | 信号 | 默认力度 |
| --- | --- | --- |
| `chat` | 短回复、协作沟通、评论、即时反馈 | `minimal` |
| `status` | 站会、进度、复盘、汇报 | `minimal` 或 `standard` |
| `docs` | 操作文档、技术说明、FAQ、事故复盘 | `minimal` |
| `public-writing` | 公众号、公开帖、观点写作 | `standard` |

只有目标明确属于子场景时才读取 Scene Pack：README 首屏说明是什么/给谁/解决什么；release note 列变更、验证和限制；forum post 保留维护者观察和社区语气；issue/PR reply 先确认问题与下一步，不做客服式安抚。Scene Pack 不覆盖 protected spans、尺度和回读规则。

## 2. 无源引用

固定从三种模式中选一种，不补机构、数据、年份或研究名称：

- `rewrite-safe`（默认 `chat`/`public-writing`）：去掉权威铺垫后，只有不依赖来源也成立的判断才保留；数字、预测或结论完全依赖无源引用时删掉整条，不把 `40%` 改成“会更快”。
- `audit-only`（默认 `docs`/`status`）：指出缺来源/缺归属，必要时保留原句；同段其他空话、黑话和结构问题仍照常处理，不把整段冻结。
- `rewrite-with-placeholder`：仅用户明确要求保留论证结构、语气或编辑框架时使用，可写“有研究认为……，但这里没有给出处”这类占位，不伪造来源。

用户未指定且文本跨场景时取较保守的 `audit-only`。`in-place` 不允许整句删除，因此无源论断采用 `audit-only`：在用户允许的形式内标明来源缺口，不改数值、不擅删句。采用 `audit-only` 且用户只要成稿、不加说明时，将来源缺口融入原句，例如“未给出处的研究声称，……”，保留其中的数值及限定，不另附说明、不增加句数；这不等于原样保留“研究表明”所暗示的已证实语气。annotation mode 只输出处理建议，不给全文改写。

## 3. 改写力度

`Tier` 描述问题严重度，`level` 描述改写强度，两者分开：

### Level

- `minimal`：文本基本自然，只删局部模板感、收尾腔和多余修饰。
- `standard`：统一语域，去工程师表演腔、商业黑话和 narrator 腔，必要时并句或换主语。
- `aggressive`：仅在 Tier 1 密集或多类结构问题叠加时使用；先保护事实和术语，`docs` 默认不升到此档。

### Scope

- `structural`（默认）：短文本、明确要求重写或 AI 味密集且无需保留节奏时，可删空句、并事实句、轻调句序。
- `bounded`：中文 `public-writing` 长文（约 1000 字以上）默认使用；不合并相邻句、不重排、不删承担节奏的实句，只删“删后信息点不变、不是唯一过渡、且纯属空话”的整句。需要可追溯时再随稿列原文和删除理由；用户只要成稿时不强制附清单，也不暂停等确认。
- `in-place`：用户要求完全原样、保句数或一句不删时使用；不删整句、不合并、不重排、不拆成新的句子，只做句内替换或缩短修饰。整句空话保留；只有用户要求标注或风险需要显式提示时，才加 `[空句，建议人工确认是否删除]`，不把提示变成额外审批。

`bounded` 中，句首“值得一提的是/归根到底/这说明”后有实质内容时句内删除，不进清单；整句只剩无源论断、价值拔高或旁白时才进入删除清单。`aggressive + in-place` 只有用户坚持时使用。

## 4. Tier

- Tier 1：开场套话、总结收尾、谄媚、商业黑话、表演性技术腔、过度共情、心理判断、身份认证式夸奖、英文 sycophancy/significance inflation/business jargon。局部用 `minimal/standard`，密集才升 `aggressive`。
- Tier 2：连接词、渲染词或姿态词在同段聚集。短段（<100 字/词）2 个以上、长段 3 个以上才标记；保留最贴切的一个。
- Tier 3：`重要/关键/核心/提升` 或 `significant/innovative/effective` 等常见词只有密度明显过高才处理；优先删多余项或写具体信息，不机械换同义词。

## 5. 保护与正向目标

保留引用原文、命令、接口/参数/字段、配置、日志、报错、系统行为主语、postmortem/incident/PRD/release note 术语和承担关键事实的抽象句。完整保护清单见 [Protected Spans](./protected-spans.md)。

每个输出里的 `X 做 Y`、`X 基于 Y`、`X 处理 Y` 要能回指原文同一谓词关系；数字要继续修饰同一对象，主体要继续负责同一动作/目标。不要把“方案”具体化成“工具/产品”，不要把“性能提升”弱化为“涉及”，不要把“提升效率”扩写成“节省时间/成本”。背景共现不是能力关系；目的、适用条件、风险和限制即使抽象也属于信息。

成稿应有具体信息、主语和动作、统一语域和可直接使用的落点；立场来自事实或判断，不靠金句、虚假主体或“我懂了”式姿态。详细目标见 [Positive Style Contract](./positive-style.md)。

## 6. 单文件基础操作

只剩入口文件时，按以下顺序处理：

1. 去开场套话、谄媚、元评论、空总结和收尾腔。
2. 将 `不是 X，而是 Y`、`与其 X，不如 Y` 直接压回 Y，除非前半句承担必要对比。
3. 把 `赋能/抓手/闭环/收窄/兜住/落盘/leverage` 等黑话改为普通动作；公文固定表达和稳定技术术语保留。
4. 把“对流程进行了优化/实现了效率的提升”一类名词化还原为动作，但不凭空补数量或效果。
5. 相邻句不要把同一对象轮换成三个更高调的说法；关键词重复可以保留。
6. 按当前句子的实际语义判断中英混排，不机械套词表。

## 7. 输出与 annotation mode

默认输出单一推荐版本，不输出过程、多版本或逐条点评。用户明确要求“先标问题”“只做诊断/审稿/标注”时进入 annotation mode；最多列 1–5 个最重要问题，每项固定包含：

```text
问题族：开场套话 / 无源引用 / 材料不足 / 工程师腔 / 语域混搭
触发点：具体词、结构或局部句子
建议动作：删除 / 换具体表达 / 补来源 / 保持不动
是否建议改写：是 / 否
```

“材料不足”只在 annotation mode 使用：压掉姿态层后事实、动作、数字和判断不足以支撑篇幅时，说明缺哪类材料，不用新说法填回篇幅。误杀边界命中时写“是否建议改写：否”。如果主要问题是缺来源，可以只给补来源建议。

高风险误杀时最多补一行短说明，例如“保留了系统主语和术语，避免失真”。

## 8. 保真回读与停止

### Pass 1

提交前核对：protected spans、事实是否丢失、语域、术语和句段衔接；再核对所有数字—对象、主体—动作/目标、抽象层级、谓词方向/完成态/强度/效果类型是否能回指原文。删句导致落点缺失时只用原文信息重组；没有可用信息就让段落变短，不补口号。

`in-place` 若字数低于原文 85%，检查是否误删整句/并句/压段；`bounded` 核对删除清单每项都是纯空话，句数变化超过约 10% 时检查是否误做 structural 改写。关键事实句、唯一过渡和有意重复不因“像模板”而默认删除。

### Pass 2（最多一次）

只有仍有明显残留才做短审计，继续受原 scope 约束：`structural` 可做一次局部删并或拆句；`bounded` 仅句内清理及按原判据删除纯空话整句，不并句、不重排；`in-place` 仅句内清理，不删、并、拆整句或重排。所有模式都不重写全文、不补事实、不改术语、参数、命令、报错或责任归属。允许范围内已无有效修正，或修正会使 `docs/status/code-context` 漂移成口语/广告语时，停在 Pass 1。

两次之后停止；“更像人”不是无限润色理由。
