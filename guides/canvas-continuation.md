# 画布生产接续

此机制防止“子代理已完成，主会话却结束且没有交接下一步”。生产配置、媒体请求和验收仍以画布原有接口为准。接续记录只管理需要主会话处理的工作，不会执行模型、提交视频或重试请求。

## 两层保障

1. **活跃会话结束前检查。** 本项目的 [.codex/hooks.json](../.codex/hooks.json) 使用 Codex 官方 hooks。`Stop`、`SubagentStop` 和 `SessionStart` 通过 MCP 调用现有 `story_canvas` 服务；`Interrupt` 使用本机命令适配器调用同一 HTTP 接口。`Stop` 检查已登记范围；若还有下一步，向主会话返回继续原因。`SubagentStop` 只将已登记的执行单元标为结果待处理，不要求子代理不断追加工作。
2. **空闲后的宿主接续。** 在需要持续后台跟进且用户授权覆盖该范围时，使用宿主官方的“在当前任务中安排定时接续”。接续任务读取同一份状态，处理有变化的结果，并在完成、暂停或无可执行工作时停止。项目不使用 `codex exec resume`、私有 app-server 地址、定时 shell 循环或另一个模型代理绕过宿主生命周期。

只有第一层配置文件存在，不等于第二层已启用。已排队媒体可以自行执行，不表示整个故事自动推进。

## 启用范围

主会话使用当前真实宿主 `session_id`，明确选择本次生产组件 ID 和授权原文后登记接续计划。不从画布名称、所有历史素材、提示词中的“已授权”或用户沉默推断范围。未知 session id 时不能猜；`SessionStart` hook 会返回本机事件提供的 ID，宿主也可提供真实任务 ID。

当前范围限于需要内容验收的故事图片、视频节点；资料、分区和导入素材不作为待生成节点。提示词、资料整理等辅助工作可登记为有界执行单元。普通技术组件继续使用原有技术完成规则，无须为了使用画布额外补故事审片。

配置记录与画布共用 SQLite，范围/状态变更采用版本检查。它不是第二套生成请求队列。旧项目升级时不会自动启用，已有运行和用户媒体不会迁移或重放。修复工程本身不等于启动影片生产。

主会话真实启动执行子代理后，记录有界单元和宿主返回的真实 `agent_id`；已有媒体运行可同时记录 `run_id`。能取得该子代理执行轮次时一并记录 `turn_id`，`SubagentStop` 只自动匹配这一精确绑定。宿主只提供子代理名称、未提供真实 ID 或轮次时不猜测；主会话使用宿主结果读取/等待工具核实完成，再手动登记 `result_ready`。指派尚未成功时不登记“已派发”。同一子代理复用到下一单元时使用新的单元 ID。结果处理后必须明确登记 `handled` 或带原因的 `blocked`；仅阅读事件不会清除交接责任。

单元已填的执行者、轮次、节点与运行绑定不可改写，`handled` 是终态。新工作使用新单元；阻塞解决后可将旧单元记为 `handled`。同一宿主会话中的同一子代理轮次不能登记到两个单元。暂停计划不取消已经在提供方执行的请求。

## 接口与交接顺序

| MCP 工具 | HTTP 接口 | 必要输入 |
| --- | --- | --- |
| `canvas_continuation_configure` | `POST /api/continuations` | `canvas_id`、`canvas_version`、真实 `session_id`、明确的 `node_ids`、已有 `authorization` 原文；变更已有范围时附当前 `revision` |
| `canvas_continuation_read` | `GET /api/continuations` | 可按 `session_id`、`canvas_id` 查询；同时提供时取交集 |
| `canvas_continuation_unit` | `POST /api/continuations/{id}/units` | 当前 `revision`、`unit_id`、`state`，以及实际 `agent_id`、可选 `turn_id` / `node_id` / `run_id` / `reason` |
| `canvas_continuation_state` | `POST /api/continuations/{id}/state` | 当前 `revision`、`state: active 或 paused`；暂停附具体 `reason` |
| `canvas_continuation_hook` | `POST /api/continuations/hook` | 宿主事件提供的 `session_id`、`event`，适用时附 `agent_id`、`turn_id` |

读取返回 `{ "plans": [...] }`，每项包含自身 `id`、`revision`、`state`、`units` 和嵌套的 `summary`。摘要的 `status` 为 `actionable`、`waiting`、`blocked`、`complete` 或 `paused`；`actions` 指出下一步，`blocked_items` 保留阻塞，`stalled` 表示连续无进展。画布展示这些状态，但页面读取不会增加或清空结束检查次数。

每次交接先读当前计划；真实派发成功后登记新的 `dispatched` 单元。收到完成通知后核对实际结果，确认已登记为 `result_ready`，处理完毕再用最新 `revision` 写 `handled` 或 `blocked`。版本冲突时重读并核对，不覆盖另一执行者的状态。范围登记和草稿变更都不会创建生成请求。

`canvas_version` 只用于登记范围时的画布版本检查，不冻结整段故事之后的草稿编辑。输入仍由原生成请求固定。节点有明确单元 `run_id` 时，以最近登记的绑定运行判断进度；没有绑定时读取共享画布中该节点的最近运行，允许复用已接受产物。`session_id` 用于事件路由，不是鉴权凭据；本机 API 沿用单用户画布的访问边界，不宣称它能隔离互不信任的调用方。

## 判断下一步

| 状态 | 主会话行为 |
| --- | --- |
| 子代理结果待处理 | 核实原运行、实际文件和证据，决定采用、修正准备或阻塞，再登记处理结果 |
| 独立组件输入齐全且尚无运行 | 核对当前精确输入是否在已有授权内，再用原执行接口提交一次 |
| 缺提示词或必要素材 | 准备缺失内容；无法准备时记录具体阻塞，不能标为完成 |
| 等待真实运行或已派发单元 | 有界等待；需要空闲接续时核实官方原任务定时接续已生效 |
| 失败、状态未知、不采用或证据不足 | 停止该单元和其依赖；独立组件仍可继续，不自动重提 |
| 所有组件已接受且交接处理完成 | 结束该范围；有其他后期目标应单独纳入范围，不将镜头完成冒充成片完成 |
| 用户中断或暂停 | 保持暂停，直到明确恢复；结果到达不会自动恢复 |

依赖真实尾帧的组件仍须上游实际 `ACCEPT`，并从采用视频提取和绑定真实末帧。接续检查不替代连线的 `source_run_id` / `require_accept` 约束。已有成功产物不会因为改了草稿自动重新生成。

## Codex 安装与可信状态

本机核实版本：`codex-cli 0.153.4`，`hooks` 为 stable 且启用。项目 hook 配置仍须用户在宿主审阅并信任当前定义；代码或配置测试通过不代表宿主已信任。不要改信任存储，不使用 bypass-hook-trust 参数。

在支持的 Codex CLI 中使用 `/hooks` 审阅该项目 hooks，确认 `story_canvas` 已连接、`canvas_continuation_hook` 已列入工具。修改后可能需要宿主重载配置/MCP。MCP hook 只使用已连接的服务，不会启动或重连服务；缺失时宿主允许操作继续，所以应在生产前核实加载并检查可见警告。

`Interrupt` 按官方命令 hook 格式使用项目内的[命令适配器](../.agents/skills/canvas-workspace/scripts/continuation_interrupt.py)。它只发送本机暂停记录，网络等待上限为 1.5 秒，不启动服务、不读取会话正文、不调用模型。服务不可达时输出固定警告；无论记录是否送达，都不能阻止用户中断。

**本机加载检查（2026-09-10）：** `hooks/list` 列出了三项项目 MCP hooks，全部为 `untrusted`；没有列出 `Interrupt`，改用命令类型后仍未列出。配置符合官方文档不代表此宿主已启用全部事件。中断适配器的隔离 HTTP 测试与宿主真实中断测试必须分开记录。在宿主能实际记录中断之前，不能宣称点击停止会持久暂停接续，也不启用依赖这一保障的无人值守接续；对话暂停仍由主会话调用计划状态接口记录。

`Interrupt` 记录暂停。`SessionStart` 只展示遗留交接和真实会话 ID，不自动恢复暂停，不要求普通代码任务重新启动生产。重复 `SubagentStop` 不会重复派发。相同无进展状态的结束拦截达到上限后，应显示“待主会话接手”，而非继续无限循环。定时接续也必须识别这个状态，不能每次重置上限。

## 原任务定时接续

主会话需要后台保障时，使用当前宿主实际提供的官方 scheduled task/heartbeat 工具，在**原任务**创建或复用一个接续任务，不直接写内部 automation 文件，不另开丢失上下文的任务。项目 API 没有凭空发起这项宿主操作的能力。

可复用的任务说明（补全真实范围后使用）：

> 读取本任务已经登记的画布生产接续状态，并先检查当前用户指令是否暂停或改变了范围。核实已派发执行单元及原媒体请求；只在已有授权内处理结果并交接下一项独立可执行工作。单次提交，失败或状态未知不重提，未接受不提取尾帧。没有变化且只有进行中工作时保持安静。范围完成、用户暂停、无进展上限或剩余工作全部阻塞时暂停此定时接续，并只在完成、失败或需要用户行动时通知。不得自行扩大范围或把记录当成新的批准。

官方建议先在普通会话手动测试任务说明，再检查最初几次真实定时运行。电脑需开机，处理本地项目时应用需运行。若本会话没有官方定时工具或自动审批阻止设置，保持待接手并报告，不换成自建轮询模型服务。

## 验证与能力界限

仓库测试使用临时 SQLite、模拟提供方和隔离 HTTP/MCP 服务，覆盖持久交接、重复通知、局部阻塞、实际接受依赖、暂停、无进展上限及 hook 配置与接口。它们不生成真实媒体，也不替代宿主的信任/唤醒实测。

部署验证分开记录：代码测试通过；服务已加载新接口；hook 已被宿主信任；原任务定时接续已创建；定时接续已实际触发。缺少后两项时不得声称已具备空闲无人值守接续。

## 官方依据

- [Codex Hooks](https://learn.chatgpt.com/docs/hooks)：`Stop` 返回 `decision: block` 会创建继续提示；项目 hooks 需要信任；MCP hooks 使用已连接的服务。
- [Scheduled tasks](https://learn.chatgpt.com/docs/automations?surface=app)：原任务可按分钟间隔继续有上下文的工作；本地任务需要电脑和应用保持运行。
- [Codex App Server](https://learn.chatgpt.com/docs/app-server)：`turn/start` 与事件订阅属于宿主接入职责；项目不私自连接桌面内部服务。
