# 项目共享生产规则

本文是当前共享的生产规则唯一来源。根 [AGENTS.md](../AGENTS.md) 只补充项目技术事实、数据边界和验证命令；历史方案、审计记录和示例只是参考，不能改变本规则。规则适用于故事、分镜、素材、提示词、视频执行和验收。

## 两种角色

项目只使用两种模型角色：

1. **主会话**使用当前会话的实际模型，负责故事、导演决定、准确对白、视觉要求、验收标准、创意修改、阻塞处理和最终交付，不承担逐步监控。
2. **执行子代理**使用用户在当前宿主配置的子代理模型与推理档位，完成一个有边界的工作单元。它可以准备提示词、准备或生成素材、检查结果和回填实际产物；正常完成时只返回结果摘要、实际产物、验收依据和未解决问题。

执行子代理不得复制主会话设置或写死型号。宿主强制传参时，仅透传已核实的有效配置；取不到不猜。新执行单元使用宿主已生效的配置，不要求运行中的代理切换模型。工作单元之外没有监控代理、项目级模型调度器或隐藏的模型切换。

## 工作单元与交接

交接只包含完成当前单元所需的信息：单元编号、冻结的源版本、当前 Panel 事实和验收标准、必要素材路径、授权范围、写入位置、适用 Skill、完成条件和升级边界。结果必须说明实际文件、采用结果、实际末态、未解决问题和依赖状态；不能用日志、推测或虚构的提供方 ID 代替结果。

一个 Panel 具备自己的时长、动作、提示词、引用素材、参数、音频或对白要求、后期责任、输出位置和必要授权后即可进入 ready。后续独立素材不阻塞已经 ready 的 Panel。依赖前一 Panel 尾帧的工作，必须等待前一结果实际 `ACCEPT` 后再取真实尾帧。视频提交仍按全局串行资源执行；其他准备、检查和回填可在实际资源允许时进行。

### 结果接续与结束条件

主会话负责结果返回后的下一次交接；“不承担逐步监控”不代表可以在工作单元完成后无人接手。收到执行结果，先核实原任务与实际产物，再记录采用、阻塞或后续处理，并实际启动下一项已授权、条件齐全的工作。发送说明、保存下一步计划或看到完成事件，都不等于下一单元已经启动。

持续生产开始时，按[接续指南](canvas-continuation.md)为当前宿主会话登记明确的画布和组件范围、已有授权原文；普通问答、代码审查和未启用接续的画布不自动纳入生产。宿主真实启动/继续子代理成功后才登记 `dispatched`；收到结果后登记 `result_ready`，主会话处理完毕再登记 `handled` 或带具体原因的 `blocked`。登记状态不是生成授权，也不能替代 `ACCEPT`。

结束本轮前读取接续检查：有待处理结果或独立可执行工作时继续交接；只有等待中工作时使用宿主有界等待，或已验证的原会话定时接续。仅在范围完成、用户明确暂停、剩余工作全部有具体阻塞，或宿主接续失效且已明确报告待接手时结束。局部阻塞不暂停整个范围。暂停或用户中断优先，不因完成事件自动恢复。

项目 Codex `Stop` hook 对已登记范围提供结束前检查，`SubagentStop` 只记录结果待处理；它们不启动生成、不更换模型、不重提失败请求。Hook 必须经过宿主信任并已实际加载才能生效；服务离线、工具缺失或钩子未启用时明确报告接续不可用，不宣称后台运行。相同状态连续触发达到上限时保留待接手并报告无进展，不把任务标为完成。需要主会话空闲后的保障时，只用宿主官方原任务定时接续，见指南；项目不新增模型调度器或私有唤醒守护进程。

## 能力、输入与授权

确认或执行前先根据当前宿主的实际能力解析输入。能力调用和 claim 使用当前会话的 `host_tools`（例如 `image_gen`、`terminal`）；项目不设置全局 host 开关。浏览器可以排队用户明确选中的已安装代理，即使当前会话没有该能力，但 claim 必须再次验证可用宿主。缺少能力时报告阻塞，保留用户选定的提供方、输入和参数，不静默换后端或改创意。

页面确认或对话授权只固定当次输入；执行子代理领取后使用固定内容，提交一次并回填实际文件。已明确覆盖同一项目范围的持续授权可复用到当前精确输入；授权范围变化或输入字节变化时重新检查。不要把沉默、等待超时或“继续”泛话当成新授权，也不增加规则之外的审批关卡。

## 实际结果与接受

技术提交成功不等于内容接受。故事生产或明确要求内容验收的媒体任务，执行子代理必须查看实际输出，并只对实际文件作一次 `ACCEPT`、`REJECT` 或证据不足时的 `INCONCLUSIVE` 判断。验收记录至少说明：实际末态（位置、朝向、姿态、手持物、接触关系、动作是否完成、空间关系和仍未知的项目）以及实际音频证据（声音、对白、停顿、同步、可懂度；无音频时明确记录）。普通文件或技术组件只需回填技术完成状态。素材、元数据、轨道存在或不确定的 ASR 不能冒充证据。

关键事实不清楚时先做一次本地复核；复核后仍不清楚就保留为未知、`INCONCLUSIVE` 或阻塞，不能强行 `ACCEPT`。`ACCEPT` 后才在确有连续性依赖时从实际视频提取真实尾帧。Canvas 普通组件没有旧包、hash 或 assembly 门槛；故事媒体结果按实际产物和内容要求验收。

确定性媒体编辑只处理已有授权范围内、执行者已核实可以删除的静音区间，不为每个区间新增用户审批。必须保留受保护的对白区间和句尾余量；ASR、VAD 只能提供待核实线索。编辑后重新检查字幕、画面、声音和音画同步，新文件仍按实际结果验收。

## 两条执行入口

### 节点画布

页面和当前宿主使用同一画布服务。修改前读取最新版本；确认后固定快照，执行者独占领取，单次提交，完成后回填实际媒体。Canvas 普通组件按快照和当前能力执行，不套用旧 LFO package、hash 或 assembly 规则。

### 旧 LFO package CLI

只有用户或任务明确选择 package CLI 时才使用它。每个包只能有当前 Panel 的一个非 `video.passthrough` Clip，路径是 `validate` 后使用批准的精确文件 SHA-256 调用 `execute --approved-sha256`。视频提交串行，每个声明工作流提交一次；已有授权覆盖当前精确包时复用，不关闭 hash 检查。所有 Panel 实际接受后，才用独立批准的 `video.passthrough` 包做一次最终组装。

Canvas 和 package CLI 共用项目 Skills、媒体边界和 Comfy 提交保护，状态与请求各自管理，不互相增加门槛。任一入口遇到提交错误、超时、hash 不符、素材不可用或适用的最小验收失败，都停止受影响的工作单元；不自动重提、不自动恢复、不把失败候选登记为正式产物。

### Comfy 提交占用

Canvas Comfy 和 package CLI 共用低层提交占用与提交回执。它是机器范围的短时互斥和持久回执，不是每个 Panel 的锁，也不引入第二套数据库。状态位于应用数据目录 `appdata/zero-to-story/video`，可由 `LFO_VIDEO_STATE` 指定；需要诊断时使用 `python -m lfo.comfy.admission`，`--reconcile REQUEST_ID` 只检查原始 Comfy `/history`，不重新提交。具体参数以运行时接口和 Canvas 指南为准。

## 创作与记录边界

主会话确定故事事实、视觉锚点、对白和验收要求；执行子代理按冻结输入完成下游工作。每个 Panel 的检查要求要能观察：数量、相对大小、身份锚点、物体形状、必须可见部分、接触关系、精确文字，以及由生成还是后期负责。记录实际时长、后端、参数和可得的资源指标；未知值留空，不写无证据的因果结论。
